# Known limitations

These are limits of the platform (an installable web app on Firebase's free plan). The app will say so on screen rather than hide them.

| Limit | Effect | What the app does |
| --- | --- | --- |
| No background location in a web app | Live vehicle position (U-02) could work only while the driver has the app open; iPhones stop when the screen locks | Not built: waiting for the owner's choice (REQUIREMENTS_TRACEABILITY.md, open question 1). With option (a), position would be sent about once a minute while the app is open. Background tracking needs an Android app wrapper or the vehicle's own tracker. |
| Free-plan limit of 20,000 writes a day | Frequent position updates eat into it | One update a minute × 6 vehicles × 12 h ≈ 4,320 writes a day |
| pdf-lib cannot lay out Kannada | Kannada text in a pdf-lib PDF comes out broken | Built in P6: the browser draws each bill page (English and Kannada alike) with the phone's own fonts, and the PDF holds those pages as images. Kannada and ₹ print correctly; the text in the PDF cannot be selected or searched. About 50 KB a page. |
| Bill numbers need the internet | A number comes from the cloud's counter in one transaction, which cannot run offline | Offline, the same bill is shared as a "Statement" without a number; "Issue bill" works once the phone is online. |
| Issuing a bill checks the phone's date against the cloud's | A phone set to the wrong day cannot issue bills | The bill screen says to check the phone's date. |
| Rules cannot add up a bill's entries | The rules check that an issued bill's own totals add up (previous + items − paid ± other = due), not that they match the ledger | The app builds every bill from the ledger with the engine (F-BILL-01, BD-02). |
| Security rules cannot hide single fields | Anything a role may not see must sit where that role cannot read it | Built in P4: a loading's purchase rate and amount are in `trips/{id}/purchases`, and a closed trip's money totals in `trips/{id}/totals`. Only owner and manager can read them. |
| Security rules cannot add up documents | Rules cannot check stock left on a vehicle, a customer's balance, or whether a trip mixes per-person labour with a labour total (D-20) | The app checks these, and trip close re-checks stock. Rules check every single document: amounts, roles, trip status, closed months. |
| A phone's offline copy is not re-checked by the rules | Data already on a phone stays readable there, even after the owner changes that person's role | Sign out empties the phone's copy. After changing someone's role, ask them to sign out and in again. |
| A driver may sell at the old rate offline | If the trip rate changes while a driver is offline, their sale at the old rate is refused when it syncs | It shows "Needs attention" (P5). The driver records it again at the new rate. |
| Two phones offline can sell the same kg | Oversold stock shows only once both sync | Trip close is blocked until stock is reconciled |
| A sale that syncs after its trip closed is rejected | The phone shows "Needs attention" with the reason ("This trip is closed") | Built in P5. How the owner re-posts it is still an open question. |
| The free plan allows 50,000 reads a day | Each phone reads its window (last month and this month) when it opens after more than 30 minutes away. Roughly: ledger entries + trip entries in the window, per phone, per cold start. Example: 150 entries and 120 trip lines a day give about 12,000 reads for the owner or manager and about 7,000 for a driver around mid-month. Eight phones opening once a day would pass the free limit. | The window stays small only if months are closed (Ledger → Close). Options if the business is that busy: the pay-as-you-go plan (reads cost a few rupees a day), or a smaller window with last month loaded on demand. Owner decision. |
| Balances on a phone start from the last month-end snapshot | A phone does not load all history, so it cannot re-add every entry to double-check a snapshot | The snapshot is made by the engine at month close and checked against a full recompute in tests (LW-*, SY-07). Checking a backup (More → Backup) recomputes every balance from all entries and reports any snapshot that disagrees. |
| A refused save is only explained while the app is open | If the phone restarts before the cloud answers, the app can still tell that a save did not arrive, but not why | After a restart it shows "Needs attention: the cloud did not accept this entry" for anything that never reached the cloud. |
| An open trip older than last month | Its sales may sit outside the window, so its totals on screen could be short | Trips are closed the same day; an old open trip should be closed or corrected first. |
| A WhatsApp link cannot attach a PDF | The link carries the bill text only | "Share PDF" uses the phone's share sheet, where WhatsApp is one of the choices. Where a browser cannot share files (most computers), the PDF is downloaded and "WhatsApp text" opens the chat. |
| Kannada wording is a first draft | Some words may read oddly | To be checked by a Kannada reader before release |
| The local emulator sign-in needs 127.0.0.1 | On `localhost` the emulator's Google screen never returns (the browser keeps the two sites' storage apart) | Open the app at http://127.0.0.1:5174 when using the emulators (SETUP_AND_DEPLOY.md). Production is not affected: the auth domain is the app's own domain. |
| No unattended backups | A Drive sign-in from a browser lasts about an hour and there is no refresh without a server | Backups happen when the owner taps "Back up now". The Backup page shows the last backup from that phone. A weekly reminder is enhancement E-05, not built (not approved). |
| A backup reads every record | One backup costs as many reads as there are records (e.g. 30,000 records = 30,000 of the 50,000 free daily reads) | Back up once a month after closing, not daily. |
| Restore runs on a computer | The rules only accept records written now by the person signed in; a record from a backup is neither | The restore tool (`npm run restore`) uses the project's admin access, adds only missing records, and never changes one (D-29, SETUP_AND_DEPLOY.md §7). The app shows the preview. |
| The browser decides whether to keep the phone's saved data | Entries waiting for the cloud live in the browser's storage. Safari may clear a site's data after about 7 days without use unless it was added to the Home Screen; Chrome keeps it once the app is installed or used often | The app asks the browser to keep its data (P8). More → Settings → This phone shows the answer, with "Keep them" when it is not kept. Install the app on every phone that records entries. |
| An installed iPhone app is separate from Safari | After Add to Home Screen the app has its own storage: it asks to sign in again, and entries still waiting in Safari stay in Safari until Safari is opened with internet (seen on the iOS simulator) | Install the app first, before recording entries. If entries were recorded in Safari, open Safari once with internet and wait for "Saved to cloud". |
| Location needs the app's secure address | The phone's location works only on https (or this computer's own address); a phone opening the dev server over Wi-Fi gets "blocked" | The shop pin can always be typed or pasted instead. On the hosted app (P9) location works normally. |
| The Drive sign-in opens a Google pop-up | An installed iPhone app may not show it | If it does not appear, back up from Safari. To be checked on real devices (DV log). |
